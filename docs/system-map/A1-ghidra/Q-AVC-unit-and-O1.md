# Q-AVC-unit-and-O1 — the reference's AV/C unit layer, and the optical-switch hang (O1)

**Date:** 2026-10-17. **Bundles:** reference = v1.11.2 `_extracted/` (asm `otool-exports/mafw.asm`, decompiles `ghidra-exports/decomp/`); ground truth = SL v1.9 (live `ioreg`, captures 76/79/80); clone = build PC 10.13.6.
**Closes:** Build rows M-Q (optical switch, O1/O2) and the AV/C part of M-C; explains O3 (23 s bring-up) and the SW-return routing bug (user report 2026-10-17).

## 1. O1 — root cause of "IsochStreamRunning during SetPacketSize"

**Observation (cited).** `FWDiscreteEngine::stopAudioEngine @0x18d8c` (asm 0x18d99..0x18dc0): `vt[0xa70]` (getState) → if 1 (running) `callq *0xa68(%rax)` → continue; the neighbouring slots are `pauseAudioEngine 0xa50`, `resumeAudioEngine 0xa58` (used by `FWEngine2::PerformFormatChange @0x124cc`, Q15c), `performAudioEngineStart 0xa60`, `performAudioEngineStop 0xa68` (IOAudioEngine vtable order, 10.13 `IOAudioEngine.h`). So the reference calls **`performAudioEngineStop`** there.
**Defect in the clone.** It called `pauseAudioEngine()`. `FWBaseEngine::pauseAudioEngine @0x3d54` is a nesting counter (`++[+0x234] < 2` → `IOAudioEngine::pauseAudioEngine`), and nothing resumed it: every play/stop leaked +1. `LogStreamState` showed `pauses 3` before the first clock change, so the pause around `SetClockSourceInternal` was a silent no-op, the isoch programs kept running, and `UpdateDCLProgramsWithNewPacketSizes` hit `IsochStreamRunning`.
**Fix.** `FWDiscreteEngine.cpp stopAudioEngine` calls `performAudioEngineStop()`.
**Verification (hardware, 2026-10-17).** Duplex client (`tools/aduplex.c`) + `tools/halwatch.c`: switch S/PDIF↔ADAT under load: no `IsochStreamRunning`, no hang, no panic; CoreAudio 16/12 ↔ 10/6 within ~8 s; the stream stalls a few seconds and resumes. Captures 76 (official), 77 (clone).

## 2. The reference's `m_audio_b_FWAVCUnit` (new finding; corrects Q-MC §1 obs. 1-2 and §3, and `FWAvc.h`)

**Observations (cited).**
* SL registry (capture 79): `m_audio_b_FWAVCUnit` is a registered child of `com_m_audio_FW1814Device` and answers an `ioreg -c IOFireWireAVCUnit` class query ⇒ **it derives from Apple's `IOFireWireAVCUnit`**. Its properties are a copy of the FireWire nub's. The device's `Unit_Spec_ID/Unit_SW_Version` = 0xA02D/0x14001 (not Apple's 0x10001), so Apple's own unit never attaches — the driver builds its own.
* Creation, `AllocateConnectionManager @0x23c72` (asm): `nub=[dev+0xe0]`; `props=nub->vt[0x2f0]`; `new` 0xF8 B; `vt[0x248](props)` init; `vt[0x670](device)` attach; `vt[0x28]()` release; `vt[0x5c0](nub)` start (**provider argument = the FireWire nub**).
* `start @0x1692` / `stop @0x165e`: guarded calls into the base class (flag byte `[+0xe0]` = the base's `fStarted`); `updateSubUnits @0x13cc`: empty (no Apple sub-unit nubs).
* `AVCCommandExtendedTimeout @0x1594`: `IOFireWireAVCCommand::withNub([+0x88] = fDevice, …)`; **stores the command in `[+0xa0]` (= the base's `fCommand`) under `[+0x98]` (`avcLock`)**, timeout 1,000,000 µs, `submit(false)`, clears `[+0xa0]` under `[+0xd0]` (`cmdLock`), release. This is how Apple's `IOFireWireAVCUnit::AVCResponse` hands the FCP response to the waiting command.
* `AVCCommand @0x17fc` (vt `0x8b0`): `new FWAsyncAVCCommand` (an `IOFireWireAVCAsynchronousCommand`, link `[+0x98]`, unit `[+0xa0]`), `init(cmd, len, FWAVCAsyncCommandCallback @0x1726, functor)`; list head `[+0xe8]`, tail `[+0xf0]`; only the head is submitted; the callback (`isPending()==false`) calls `FinishAsyncCommand @0x16c8` (pop, submit next, release). **Selector, feature-block and mixer-connect commands use this async path with no functor** (decomp `FWAVCAudioDevice__AVCSelectorCommand.c:38`, `…FeatureFunctionBlock.c:40`, `…AVCMixerConnectSingle.c`); **plug format and the HSCI frame use vt `0x8b8`** (sync, retrying).

**Defect in the clone.** `FWAvcUnit` was a bare `OSObject` and used `IOFireWireAVCCommand::withNub` against the nub with no `IOFireWireAVCUnit` anywhere; `fFCPResponseSpace` was never registered, so **no FCP response was ever delivered**: every command timed out after ~1.27 s (the device still executed it — rates changed and locked). The mixer-connect pair stopped after the first timed-out single, so the right channel of "SW return 1/2 → out 3/4" never went out (user-reported bug). Capture 79 has the before/after logs.
**Fix.** `FWAvc.{h,cpp}`: `com_openaudio_FWAvcUnit : IOFireWireAVCUnit` built as above (`Setup(device, nub)` from `AllocateConnectionManager`), `start/stop/updateSubUnits` as the reference, sync command with `fCommand`/`avcLock`/`cmdLock`, async queue (`AVCCommandAsync`, `FinishAsyncCommand`; the clone adds a lock because its callers and the completion run on different threads). Selector, feature block and mixer connect go through the async queue.
**Verification.** `ioreg` shows `com_openaudio_FWAvcUnit` as an `IOFireWireAVCUnit`; sync command `r=0x0`, response `0x09`, 22 ms (was 1,256-1,275 ms timeouts); bring-up 23 s → 13 s; user: "SW 1/2 → out 3/4 works". Not yet verified: 5-minute stability, bus-reset / sleep-wake behaviour of the unit, `kextunload` with commands queued.

## 3. Audio MIDI Setup sidebar "N ins / M outs" — still open

**Observations.** Official driver on the SL: the sidebar updates (captures 78a/78b); stream object ids stay the same (264/265, capture 76) — in-place change, as in the clone. Clone on 10.13: the HAL reports the new counts (`system_profiler`, `aduplex`), the notification burst is complete (`ownd`, `slay`, `diff`, `pft/pfta/sfmt/sfm#` on device and streams, capture 77), AMS re-reads `slay` and receives 16/12 (capture 78), the pane updates ("12 ch", ADAT rows), **but the sidebar label stays "10 ins / 6 outs"** (78c). Reselecting the row, a rate change, and a default-device toggle do not refresh it. Mirroring the official stream format (alignment 0, format extension; asm `SetStreamFormat @0x4192`) did not change it.
**Evidence added (2026-10-17, user observation, capture 82 §5):** after the kext reload with the interface already in ADAT the sidebar read **16 ins / 12 outs**, i.e. a freshly added device gets the right label; only the in-place change does not refresh it. This is the outcome the check below predicted.
**Resolved then withdrawn (2026-10-17, R60 + correction):** re-publishing the device at optical switches makes the sidebar follow (capture 83) but kills live clients, so it is disabled; the in-place reference path is used and the label may be stale. The hypothesis below was therefore sufficient as a working explanation; the mechanism inside AMS was not inspected.
**Hypothesis (supported, not proven).** 10.13's AMS builds the label when the device is added. **Check:** open AMS while already in ADAT; if the label then reads 16/12, an in-place change cannot refresh it and a HAL re-publish would be needed (a 10.13 deviation). Not done.

## 4. Other corrections from the same run
* `FWHsci::Release` must not call `IOFWCommand::cancel()` synchronously: `FW1814Device::stop` runs on the termination thread and `kextunload` hung uninterruptibly (no panic). The `retain()` held during every read already pins the object and the kext; command and buffer are freed in `free()`.
* `SetStreamFormat`: alignment byte is 0 = `kIOAudioStreamAlignmentLowByte` (10.13 header: LowByte 0, HighByte 1); the clone had published HighByte (1). The official format dictionaries carry `FormatFlags 0`, `FramesPerPacket 1`, `BytesPerPacket = channels×4` (capture 67c); the clone omitted the extension.
* F4 (clone addition: write the headphone selectors at start-up) **reverted**: the reference leaves `Reg 0x98` unwritten until a monitor source is chosen, and the phone levels start at 0 dB. Panel addition: caps phone levels at -86 on open and restores the last settings per GUID.
* MASampleRate panel path (capture 80): the official kext also keeps the old `MASampleRate` and drops `MARateLocked` after a panel write; the official panel keeps the chosen rate in red. The clone's panel reverting is a panel display rule, **not yet fixed**.
