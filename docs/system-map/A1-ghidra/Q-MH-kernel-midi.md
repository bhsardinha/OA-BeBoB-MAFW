## Observations (cited)
1. **Ports** (`TKernelMIDIPort::Init @0x1e64a`, struct 0x28 B): `[+0]` rx base, `[+8]` read index, `[+0x10]` timestamped ring, `[+0x18]` realtime ring, `[+0x20]` descriptor `IOBufferMemoryDescriptor::withOptions(0x10003, 0x2000, page)` (user/kernel shared, 8 KiB). Source ports (device→host, `0x400+n`): `u32` write counter at +0, 0x200-byte byte ring at +4 (the RX callback stores `count % 0x200`). Destination ports (`0x800+n`): rings of `{u32 head, u32 tail, 128 × 16-byte slot}`; timestamped ring at +0, realtime ring at +0x808. Slot = `{u64 ns timestamp, u32 length (≤4), u8 data[4]}` (`TMIDIPort::CheckForNewRealtimePacket @0x1e7b2` / `CheckForNewTimestampedPacket @0x1e7fa`: slot = base + 8 + 16·tail; consuming = `tail = (tail+1) mod 128`; the timestamped check consumes only when `slot.time − now < window`). `TMIDIPort::Clear @0x4d36` zeroes the read index and the three regions (0x204, 0x808, 0x808). `CheckForNewBytes @0x1e6e8` (byte-ring reader, 2-segment descriptor) has no kernel caller found.
2. **Engine fields = the shared sync block:** `[+0x298]` (MIDI running) is `FWDCLSharedSyncData +0x58`, `[+0x29c]`/`[+0x2a0]` the source / destination counts (`+0x5c`/`+0x60`), `[+0x2a8]` destination array (`+0x68`), `[+0x2b0]` source array (`+0x70`) — the DCL programs read them through the shared pointer (`this+0x80`). `SetMIDIInputPorts @0x5226` / `SetMIDIOutputPorts @0x5160` (output count clamped to 8): refused while MIDI runs; free the old array, `new[count × 0x28]`, `Init` each, then `SetMIDIPortProperties @0x5028`: device property `MAMIDIInputPorts` / `MAMIDIOutputPorts` = `OSArray` of names ("1","2",… when none given), removed when the count is 0. FW1814 `SetupAudioEngine` asks for 1 + 1 ports.
3. **Start/stop:** `FWBaseEngine::StartMIDI @0x4118`: running → `0xE00002D2`; no ports → `0xE00002C7`; `StartIsochStreams` (vt `0xc18`), on success running := true. `FWEngine2::StartMIDI @0x120d4`: same guards, `StartIsochStreams`, `IOSleep(600)` when that took the first isoch reference (`[+0x22c] == 1`), then the base start (a second reference), and `StopIsochStreams` if that failed. `StopMIDI @0x40f6`: running := false, `StopIsochStreams`; `FWEngine2::StopMIDI @0x11b86` stops the base reference and one more. `StopMIDIAndClearBuffers @0x4d78`: `StopMIDI` (vt `0xcf8`), and on success `Clear` on every port. `SendMIDI @0x3eb2` returns `0xE00002C7` (the FW1814 does not implement selector 503).
4. **TX path (`ProcessCompoundMIDIOutput @0x26be6`, called from the RX segment handler on every even segment with a byte budget of 3 per port):** per destination port — realtime packets first (a packet that places no byte is put back), then timestamped packets due within 20 ms; consecutive stamps are forced ≥ 1 ms apart (`[+0x5d8+8·port]`); a packet longer than the budget is truncated, the unsent tail is moved to the front of the slot and the slot is put back (`tail−1`). `ScheduleMidiPacket @0x26ab2`: `pos = max(port/mode cursor [+0x558+16·port+8·mode], ConvertTimestampNanosToAbsPacketIndex(stamp, now))`; at most 200 tries; a candidate packet index is moved out of the 4 primer packets of its group, the packet must carry data (SYT ≠ `0xFFFF`) and its MIDI slot (quadlet `2 + audioQ + port·(audioQ+1)`) must be `0x80` (empty); a taken or NODATA packet advances by 1, an eligible packet skipped because the cursor is ahead advances by 8; a byte is stored as `0x81 | byte << 8` and the next candidate is the following packet (a message longer than 3 bytes places nothing). `ConvertTimestampNanosToAbsPacketIndex @0x26a06`: stamp 0 or < 4 ms ahead → now + 4 ms; index = packets-per-lap × lap + first active packet of the bank after the latest history entry + (Δns·8000 + 12.8e9)/1e9. `Output::Start` clears cursors and last stamps of the destination ports.
5. **RX path:** `ProcessCompoundMIDIInputForPacket @0x2525c`: for every data block the MIDI quadlet at `audioQ + b·blockQ` with label `0x81` stores its data byte in source port `b mod 8` (only ports below the source count); the M-B port was written from this decompile and matches the port layout above.

## Open / unverified
* The ring slot timestamps use the host clock in nanoseconds (`clock_get_uptime` → ns, as the reference): the user-space writer must use the same clock (A3-M5/M6 say the reference plug-in does).
* Behaviour of the two-reference isoch hold of MIDI against the audio stream start at the integrated run.
* `CheckForNewBytes` and `ReceivedMIDIPacket`'s type-1 push have no caller in the kernel path found so far.

## Plug-in decision (Build row M-H2)
The reference plug-in (`_extracted/midi/MAudioFireWireMIDI.plugin`, universal x86_64+i386, 64-bit slice loadable by MIDIServer) is **reused unmodified**. It finds the device with `IOServiceMatching("com_m_audio_FW1814Device")` (A3-M2 §1, strings in the binary), opens a user client of type 0, calls selectors 500/501, maps `0x400|n` / `0x800|n`, reads `MAMIDIInputPorts` / `MAMIDIOutputPorts` and polls the rings every 666 µs (A3-M3/M5/M6/M7). The clone satisfies each of these: the abstract alias class `com_m_audio_FW1814Device` (FWAudioDeviceChain.h) makes the name match by inheritance, `IOUserClientClass` in the FW1814 personality supplies the client, selectors and memory types are Q-MF / this note. **unverified:** that the plug-in loads on 10.13.6 and that `EntryStartMIDI`'s busy code (`0xE00002D2` while MIDI already runs, `kIOReturnBusy` semantics A3-M5) matches what its retry loop expects; both are checked at the integrated run. The installer (IN.5) must copy it to `/Library/Audio/MIDI Drivers/`.
