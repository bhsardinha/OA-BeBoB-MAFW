## P1 — device discovery: **verified with corrections**
* `CXDevice::CXDevice(MAIOKitService*, bool)` @0x6c2b8 (Ghidra a2-batch1.log:49-170; asm 0x6c502-0x6c54a): `[mas openConnection]`, then — **only if the bool is true** — `IOConnectMapMemory(conn, 1, mach_task_self(), &this[+0x68], &len, 0x1001)`. The bool is the P9 `createSharedMem`; the old label `mapMIDI` and the sentence 'type-1 shared buffer is the MIDI packet ring … MIDI-activity LEDs' are **wrong**.
* Kext side (`mafw.asm`): `FWUserClient::clientMemoryForType @0x7220` for type 1 returns `FWAudioDevice[+0x100]` with size `0x1000`; that descriptor is created in `FWAudioDevice::initHardware` as `IOBufferMemoryDescriptor::withOptions(0x10000, 0x1000, 0x1000)` (0x3598-0x35ac) and `GetPeakLevelCount` = 0x34 (52 × u32). So **type 1 = the 4 KiB peak-meter page** (Q-UC-surface §3). MIDI rings are other types (0x400+n and 0x800+n, kext tables `[eng+0x2b0]/[eng+0x2a8]`; which is in/out is **unverified** here).
* The ctor also (per decomp, missing from P1): `FetchCoreAudioDevices`, `MXDevice initWithDevice:`, reads `nominalSampleRate`, seeds its property cache `this[+0x6c]` from the device property **`MAMetaAllProperties`** (`addEntriesFromDictionary:`), reads `MAFirmwareInfo` with `getBytes:length:0x50` into `this[+0x88]` (80 bytes — matches the kext's 0x50 read), `pthread_create(TerminationWaitThread)`. Kext side: `FWPropertyDict::CopyProperty` special-cases `MAMetaAllProperties` → `CopyAllProperties()` (`mafw.asm` 0xa237-0xa24d).
* Notification registration: `MAServiceNotification initWithDictionary:port:type:target:selector:` @0x8108d passes the caller's `type` string straight to `IOServiceAddMatchingNotification` and then **immediately drains the iterator** by calling `ServiceDispatchCallback` once; panel strings contain `IOServiceMatched` and `IOServiceTerminate` and **no** `IOServicePublish` (P1's call-chain text is wrong on that string). The matching dictionary is keyed by `IOProviderClass` (retained at `+0x14`). All 8 product class names are present in the panel (`strings`), so registration is per product class, not 'two dictionaries'. `CDeviceList::AddDevice` takes an `unsigned long` (io_service_t), not a `MAIOKitService*`.

## P8 — rate/buffer: **verified**
* `CHardwareView::ListenToMessage @0xd7108`: codes `0x1466`, `0x1465`, `0x613`, `0x614`, `0x1451`, `0x5ff`, `0x602`, `0x601` all present (asm 0xd717d-0xd748d); outbound `0x1465→cookie 0x613`, `0x1466→cookie 0x614` as P8 §3.2 states.
* `LoadSupportedSampleRates @0x664b0` uses cookies `0x603` (count) then `0x604` (array) (0x664da, 0x66554). `SendNewSampleRateTimer @0x6c8c8` is Obj-C messaging; the panel contains the selectors `nominalSampleRate` / `setNominalSampleRate:` (CoreAudio path, not a property write) — consistent with SL capture 65 (rate change surfaced as an `IOAudioStreamFormat` update).
* ASIO/driver-buffer cookies stay vestigial on Mac (memory `project_mac_vs_windows_scope`).

## P10 — AC3: **panel claim verified, kext claim REFUTED**
* Panel: `strings` finds **0** matches for AC3/Passthrough/Passthru/NonAudio/Dolby/IEC958/IEC61937 — verified.
* Kext: `SupportsAC3` vtable slot is `0xaa8`. `m_audio_b_FWAudioDevice::SupportsAC3 @0x1c40` returns **1** (`movl $1,%eax`). `FW1814Device` slot 0xaa8 → `0xc318`, also **returns 1**; other overrides at 0xa97e, 0x1291c, 0x13614, 0x13992, 0x17468, 0x1a4d2, 0x1f3fa, 0x2292c return 1; only `FWOzonicDevice::SupportsAC3 @0x16960` and `FWNRV10Device::SupportsAC3 @0x1a162` return **0** (`xorl %eax,%eax`). So **the FW1814 already advertises AC3 in the reference**; P10 §2-3 ('base returns 0 … FW1814 inherits 0 … enable it as a cheap win') and A1-Q12:147 ('base returns false @0xaff6') are wrong. The AC3 path ([+0x2d4], `EnableAC3Format 0x44ab`) is live for the FW1814, and the clone must **mirror it**, not 'add' it.
* The P10 §3.3 'enable as feature-parity-plus' recommendation is withdrawn (it also conflicted with the project rule against scope the reference lacks — here the reference has it).
