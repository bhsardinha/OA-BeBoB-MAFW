# A3 MIDI plug-in — static audit against the binary (2026-10-14)

Scope: M1, M2, M8, M9 (matrix items `A3-M1.1, M2.1, M8.1, M9.1`). Bundle: **v1.11.2** `_extracted/midi/MAudioFireWireMIDI.plugin` (CFBundleVersion 1.11.2, built Xcode 4.6.3 / SDK 10.7). The doc addresses (e.g. `_NewFW410MIDIDriver @0x1be6`, `TMIDIParser::ParseMIDIByte @0x4b9c`) are the **x86_64 slice**; `otool -tvV -arch x86_64` reproduces them. Evidence for M2 live data: SL v1.9 `B5-sl-dtrace-truth/captures/12-ioreg-full.txt`.

## M1 — factory + driver interface: **verified**
* `Info.plist`: factory `29F28FC6-B0F8-11D7-B850-000393942016` → function `NewFW410MIDIDriver`; type `ECDE9574-0FE4-11D4-BB1A-0050E4CEA526` (kMIDIDriverTypeID); bundle id `com.m-audio.midiplug.fw410`; `CFPlugInDynamicRegistration=NO`.
* `_NewFW410MIDIDriver` (0x1be6): `CFUUIDGetConstantUUIDWithBytes(0xEC,0xDE,0x95,0x74,0x0F,0xE4,0x11,0xD4,0xBB,0x1A,0x00,0x50,0xE4,0xCE,0xA5,0x26)` + `CFEqual`; on match `operator new(0x20)` (0x1c81-0x1c86), `MAFWMIDIPluginGlueBeBoB::MAFWMIDIPluginGlueBeBoB()`, returns `obj+8` (0x1c96).
* `MIDIDriver::MIDIDriver(CFUUIDRef)` (0x194a): `[0]=vtable`, `[8]=&MIDIDriverInterfaceFtbl`, `[0x10]=factoryUUID`, `CFPlugInAddInstanceForFactory`, `[0x18]=1` — the refcount store is `movq $1` (8 bytes), not a 32-bit field as M1 §3 says (cosmetic).
* `MIDIDriverQueryInterface` (0x19f4): `kMIDIDriverInterface2ID = 43C98C3C-306C-11D5-AF73-003065A8301E` → `vt[0x10]` (retain), `*out = this`, `[this+0x14] = 2` (0x1ab4); IUnknown branch follows.

## M2 — device discovery: **verified with one correction**
* `createDeviceProperties:withService:` constants in the binary: `MIDIObjectSetIntegerProperty` with `0xC35` (3125), `0xFFFF`, `0xFFFF`, `0x3A98` (15000) (0x3776, 0x378c, 0x37a2, 0x37b8). Matches M2 §3.
* Kext→plugin contract keys are live on the SL rig (v1.9): `IOAudioDeviceName = "FireWire 1814"`, `IOAudioDeviceManufacturerName = "M-Audio"`, `MAIconName = "FW 1814"`, `GUID = 3777939140557307` (decimal in ioreg; the plugin formats it as `%llX`), and **`MAMIDIInputPorts = ("1")`, `MAMIDIOutputPorts = ("1")`** (`12-ioreg-full.txt:3933-3951`).
* **Correction:** M2 §8.2 hypothesised `["In 1","In 2"]` / `["Out 1","Out 2"]`. The reference publishes **one** input and **one** output port, each named `"1"`, matching the FW1814's single MIDI I/O pair. (The array shape is NSArray of NSString; the strings are the port names CoreMIDI shows.)
* §7 'both share one user client' stays **unverified**: SL ioreg shows the Panel and the helper each hold their own `FWUserClient` (B5 §3); what the MIDI server holds is not captured (B5:530 'presumably').

## M8 — SysEx: **verified**
* `ParseMIDIByte` (0x4b9c) contains `movl $0xdd,%edx` (realtime mask, 0x4bcb), `cmpw $0x100,%cx` (scratch-overflow threshold, 0x4c11), `movl $0xffffff,(%rdx)` (sysex sentinel, 0x4ce8) and the running-status field at `rdi+0x21c` (0x4d5b), as M8 §2 states.
* Still **hypotheses** (not checkable statically): that `fDestPortInSysex` is consumed by the kext; behaviour for undefined bytes 0xF4/0xF5.

## M9 — sleep/wake: **verified with one hypothesis resolved**
* `_SleepNotificationCallback` compares the message against `0xE0000270`, `0xE0000300`, `0xE0000280` (0x43a4, 0x43ac, 0x43fc) — can-sleep / has-powered-on / will-sleep as documented; `kIOMessageSystemWillPowerOn` is not handled.
* Resolved: the factory's `systemWillSleep` (0x3c48) / `systemWokeUp` (0x3c30) are **tail calls to the class methods `+[MAFWMIDIDeviceBeBoB systemWillSleep]` / `+systemWokeUp`** (receiver = the class object loaded from the Objc class ref, `jmpq *…(%rip)` at 0x3c5b/0x3c42) — not an iterator or NSArray `makeObjectsPerformSelector:`. M9 §4's 'hypothesis' is therefore replaced by a read fact; what the class method does with `sDrivers` is not re-decoded here.
